# Steadfast courier setup

1. Open **Configuration > Courier Configuration > Steadfast** in the admin sidebar.
2. Enter your Steadfast API Key and Secret Key, enable the integration, review the status mappings and save. The API address now defaults to `https://portal.packzy.com/api/v1`, matching the supplied merchant documentation. The legacy `https://portal.steadfast.com.bd/api/v1` address is also selectable. Only those provider addresses are allowed; redirects are disabled. Blank secret fields preserve existing credentials. Secrets and the webhook token use Laravel encrypted casts; keep APP_KEY stable and backed up. Main-account API keys and webhooks must belong to the same profile; business-profile keys cannot read main-account parcels.
3. Check Connection & Balance performs a read-only balance request. Saving does not send orders.
4. Copy the Callback URL and generated Bearer Token into the Steadfast merchant panel webhook settings. Use a public HTTPS APP_URL. `.test` / localhost URLs cannot receive provider callbacks. Forward Authorization headers through your web server. No API credentials belong in URLs.
5. Keep a database queue worker running for realtime processing: `php artisan queue:work database --queue=default --tries=3 --timeout=60`. Configure server cron to execute `php artisan schedule:run` every minute; it also recovers pending inbox events every minute if queue dispatch/processing was interrupted. For a local development scheduler use `php artisan schedule:work`. Use a persistent shared database or Redis CACHE_STORE on multiple application servers so booking locks work across nodes. Do not start a worker until you intend pending outbound notifications to be sent as well.

## Booking and status

Order List > courier dropdown > Assign Steadfast submits a real parcel with the saved recipient, invoice, local Bangladesh mobile number, outstanding order COD and note. Other courier providers retain local assignment only. Previously assigned Steadfast orders have no API booking until explicitly assigned through this action. No existing orders are sent automatically.

Orders retain a unique shipment per order/invoice. A reservation is committed before the network call. Double clicks and concurrent booking attempts are blocked. Timeouts and ambiguous provider failures are never automatically rebooked. Authentication rejection (HTTP 401/403) permits retry after credentials are fixed. For another unconfirmed request, first search the invoice in the merchant panel and Sync Status. If the invoice definitely does not exist there, the order view provides an explicit confirmation to clear the reservation after two minutes. Clearing it does not cancel a parcel or submit another one.

The order view shows booking state, consignment ID / tracking code when returned at booking, COD, last successful sync, safe error messages and the last ten courier status changes. An uncertain booking recovered by invoice can have a verified status without its consignment/tracking identifiers, since the status endpoint does not return them.

Webhook authentication now checks BOTH `Authorization: Bearer TOKEN` and `X-Signature`. The signature is hexadecimal HMAC-SHA256 of the exact raw request body keyed by the same token. The webhook response does not call the courier API: it saves an encrypted durable inbox record, queues processing on the database connection, and returns HTTP 202. This keeps courier HTTP latency out of Steadfast's five-second response window. Invalid authentication/signature returns 401, malformed event envelopes return 400, and failure to persist returns 503 (provider retries). The provider retries server/network failures after 30 seconds and two minutes, but does not retry 4xx responses.

`Idempotency-Key` is hashed and stored uniquely; duplicate retries are acknowledged without another job. Reusing a key with a different body returns 409. Raw-body hash is used if the key is absent. Signed delivery_status events use provider `updated_at` ordering to ignore stale / repeated status changes and apply the configured status mapping directly in the worker. Offset-free provider timestamps are interpreted as Asia/Dhaka. COD amounts in webhook payloads do not mutate order financial records. Consignment IDs must match when known; a lost booking identifier can be recovered from a valid signed delivery event.

Other event types (tracking_update, consignment_update, return_list_accepted, cancel_request, return_request) can omit delivery status. They reconcile asynchronously, never fail the callback for lacking invoice/status fields. Account-level return-list acceptance flags managed return shipments for a fresh scheduler lookup. Unrelated account/payment/pickup events and unmanaged invoices are acknowledged and marked ignored. No payout is automatically posted as a customer receipt. Recent webhook processing outcomes appear in the configuration page; raw recipient payloads and keys are not displayed. Refresh the order page to see saved updates.

The scheduler reconciles up to 30 eligible shipments per five-minute run, oldest checked first, with overlapping runs prevented. Large backlogs may take additional cycles. Each parcel's status reads are at least 60 seconds apart, matching provider caching. A recently applied signed webhook is protected from a stale cached API response. When a consignment ID is known, sync uses status_with_return_status_by_cid; otherwise status_by_invoice. Return-processing / rider-assigned / received states are retained and configurable in status mappings. Cancelled and partially delivered parcels keep polling until the return is received. Delivered and return-received shipments stop automatic polling; subsequent webhooks and manual sync can still reconcile corrections.

HTTP 401/403 sets an authentication block: background API calls stop until corrected keys are entered and saved again. HTTP 429 pauses requests according to numeric Retry-After (or one hour if absent). Saving keys does not bypass this provider cooldown. HTTP 422 gives a safe field-validation error. No automatic booking retry loops are used. Recipient names and invoices over 100 characters or addresses over 490 characters are rejected locally to avoid silent provider truncation; notes are capped at 480 characters.

Default mappings are Processing for in_review, Shipped for pending, Delivered for delivered, Cancelled for cancelled (matched by status name, never hard-coded IDs). Save them on the configuration page. Unmapped states only update courier information. Approval-pending / hold / unknown / partial delivery do not falsely mark orders completed or returned. Configure mappings to your business workflow. Existing payment receipts, stock and returned quantities are not changed by courier callbacks; partial delivery and settlement need admin reconciliation. This is shipment tracking, not financial settlement.

Once a reservation exists, products, recipient and order totals are locked against local edits to avoid diverging from the parcel and COD. The separate Status action remains available. Courier switching is blocked for Steadfast bookings. Duplicating an order starts a separate order with no shipment.

## Cancellation

**Cancel Local Order** in the Steadfast card requires a cancellation reason and records local Cancelled status/history. Cancel the actual parcel in the Steadfast merchant panel as well. The published Steadfast package documents booking, delivery status, balance and webhook APIs, but no direct parcel cancellation endpoint; no undocumented cancellation request is sent. Subsequent courier sync follows the actual provider state and can supersede a local status. Courier-reported cancellation has a recorded courier reason if no customer reason exists.

Reference: merchant API and webhook guideline screenshots supplied by the user (Packzy/Steadfast, November 2026). No undocumented cancellation endpoint is assumed from a cancel_request event name.

No live booking, credential check, webhook or tests were run during implementation. Configure real credentials and the public callback in the provider panel before use.
